The 30-second answer

I built the skeleton every later module plugs into: a FastAPI app factory, settings from environment variables, and Postgres 17 in Docker Compose with a healthcheck.

Every request gets an ID that comes back in X-Request-ID and is attached to every log line. Every error, from a bad field to an unhandled bug, returns RFC 9457 problem+json carrying that same ID. A user can quote one ID and I can find every log line for their request.

What I built

  • App factorycreate_app(settings) wires settings, the database engine, middleware, error handlers and the router.app/main.py
  • SettingsRead from environment variables, then .env, then defaults that match Compose.app/core/config.py
  • Health checkRuns SELECT 1. 200 when the database answers, 503 when it does not.app/api/health.py
  • Request-ID middlewareKeeps a safe incoming ID or makes one, adds it to the response and the logs, writes one access line per request.app/core/middleware.py
  • JSON loggingstructlog and the standard library share one formatter, so uvicorn and SQLAlchemy lines look the same as ours.app/core/logging.py
  • One error formatAppError subclasses plus handlers for 404, 405, 422 and unexpected 500s.app/core/exceptions.py
  • Database engineOne connection pool per process, lazy, pre-pinged, 3-second connect timeout.app/infrastructure/database/engine.py
  • ContainersPostgres 17 with a named volume and pg_isready healthcheck; a cached, non-root API image.docker-compose.yml Dockerfile
  • Tests12 unit tests (errors, health, request IDs, JSON logs) and one integration test against live Postgres.tests/

One request, start to finish

  1. 1
    Request arrives

    uvicorn calls the ASGI app: async def app(scope, receive, send).

  2. 2
    Middleware tags it

    Keeps the caller's X-Request-ID if it is short and plain, otherwise makes one. Binds it to the log context and to request.state.

  3. 3
    The route runs

    /api/v1/health borrows a pooled connection and runs SELECT 1. It is a plain def, so it runs in the thread pool.

  4. 4
    Anything raised becomes problem+json

    A handler builds type, title, status, detail, instance and request_id. Business code never builds HTTP responses itself.

  5. 5
    Response leaves

    The middleware adds the X-Request-ID header and writes one access line with method, path, status and duration_ms.

Decisions

Shape of the app

An app factory, create_app(settings)

Instead of an app built line by line at import time

Each test builds a fresh app with its own Settings, so nothing leaks between tests. uvicorn still imports app.main:app.

Settings default to the Compose values

Instead of required config or hard-coded values

A fresh clone runs with zero setup. Real deployments override through environment variables: env beats .env beats defaults. Tests pass _env_file=None so a developer's .env never changes results.

Plain def routes for database work

Instead of async def

SQLAlchemy here is synchronous. A blocking call inside async def freezes the event loop for every request; FastAPI runs def routes in a thread pool instead.

A lazy engine with pool_pre_ping and a 3-second timeout

Instead of connecting at startup

The app boots while Postgres is down, and /health reports it. Pre-ping swaps out connections that died while idle. The timeout stops the health check hanging.

Logs and errors

A plain ASGI middleware

Instead of Starlette's BaseHTTPMiddleware

BaseHTTPMiddleware wraps every response in an extra stream and stops context-variable changes from flowing back up. A plain ASGI class is a few more lines and sees the raw response-start message, which is where the header goes.

Accept a caller's ID only if it matches [A-Za-z0-9._-]{1,64}

Instead of trusting any header value

A gateway or client can still trace a request end to end, but nobody can inject newlines or fake JSON into the logs through a header.

structlog context variables carry the ID

Instead of passing request_id through every function

Bind once in middleware; merge_contextvars adds it to every line. Context variables belong to the current task, so concurrent requests never mix IDs.

RFC 9457 problem+json for every error

Instead of FastAPI's default {"detail": ...}

One shape everywhere. type is stable for client code to branch on, title is the same every time, detail explains this occurrence, and request_id links it to the logs.

422 bodies leave out the rejected input

Instead of FastAPI's default, which echoes it back

On /auth/register the rejected input contains the user's password.

Health answers 503 when the database is down

Instead of 200 with an error in the body

Docker, load balancers and uptime monitors act on the status code alone. The body is a status report, not an API error, so it is plain JSON, not problem+json.

Containers

Services in Docker, the API on Windows with --reload

Instead of running everything in containers every day

Fast reloads and easy debugging. The containerised API exists for the M8 race test and the load tests. Celery and Redis do not support Windows, so they will always live in containers.

A cache-friendly, locked, non-root image

Instead of copying everything and installing in one step

pyproject.toml and uv.lock are copied before the code, so editing code does not reinstall packages. uv sync --locked fails on a stale lock file. The server runs as uid 10001, never root.

depends_on: condition: service_healthy

Instead of a plain depends_on

A started container is not a database that accepts connections. The API waits for pg_isready.

* text=auto eol=lf in .gitattributes

Instead of Git's Windows default of CRLF line endings

A script saved with CRLF fails inside a Linux container with $'\r': command not found.

Interview questions

Answer out loud first, then open.

What is the difference between an image and a container?

An image is a read-only, layered template built from a Dockerfile. A container is one running instance of it, with its own writable layer, process and network identity. Many containers can run from one image, and deleting a container leaves the image untouched. Data that must survive a container goes in a volume, which is why Postgres writes to pgdata.

Why does the API container reach Postgres at db:5432 while your laptop uses localhost:5432?

Compose puts both services on a private network with its own DNS, so the service name db resolves to the database container. Inside a container, localhost means that container itself. The "5432:5432" port mapping publishes the container's port on the host, which is how tools on Windows reach it at localhost.

How does every log line get the request ID without passing it around?

The middleware calls bind_contextvars(request_id=...) at the start of each request, after clearing the previous request's values. structlog's merge_contextvars processor copies whatever is bound into every event. Context variables are scoped to the current task, so two requests running at once each see only their own ID.

Why is the health route def and not async def?

It calls synchronous SQLAlchemy, which blocks while it waits for Postgres. Inside async def that wait would freeze the event loop that serves every other request. FastAPI runs plain def routes in a thread pool, so the blocking call only ties up one worker thread.

Why return 503 from /health instead of 200 with an error message?

Orchestrators, load balancers and monitors decide on the status code without reading the body. A 503 takes the instance out of rotation or raises an alert; a 200 would say all is well. The body still says which check failed, for humans.

What is ASGI, and why write the middleware at that level?

ASGI is the interface between an async Python server and the app: async def app(scope, receive, send). scope describes the request, receive yields the body, and send is called with the response start and then the body. A middleware wraps the next app; mine wraps send to add a header to the response-start message and record the status. Working at this level avoids BaseHTTPMiddleware's extra response stream and its context-variable limitation.

What are the fields of an RFC 9457 problem, and which one should a client branch on?

type (a URI naming the kind of problem), title (short, the same for every occurrence), status, detail (this occurrence) and instance (the path). Clients branch on type, because titles and details are prose that may change. Extra members are allowed; I add request_id, and errors for 422s.

What does pool_pre_ping cost, and what does it buy?

One cheap round trip each time a connection is taken from the pool. In return, a connection that died while idle (Postgres restarted, a firewall dropped it) is replaced silently instead of failing the request that happened to get it.

Why copy pyproject.toml and uv.lock before the code in the Dockerfile?

Docker caches each step and reuses it until its inputs change. Dependencies change rarely and code changes constantly, so installing dependencies first means a code edit rebuilds in seconds instead of reinstalling every package.

Traps and fixes

  • uvicorn brings its own log handlers. I cleared them so its lines reach the JSON handler, and disabled uvicorn.access, which would duplicate the middleware's access line without the request ID.
  • Configuring logging twice printed every line twice. Our handler is named and replaced on each call, and other handlers, such as pytest's log capture, stay in place.
  • The catch-all 500 handler runs outside the middleware. Starlette's outermost error middleware handles it, so that handler adds X-Request-ID to the response itself.
  • libpq treats a connect_timeout below 2 seconds as 2.
  • Compose substitutes $VAR before the container sees it. The healthcheck uses $$POSTGRES_USER so the container's shell expands it instead.
  • Error messages can leak secrets. Health logs only the first line of the driver's error, which names the host and port, never the password.
  • Port 8000 can only have one owner. Stop the api container before running uvicorn on Windows.
