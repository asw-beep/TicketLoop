The 30-second answer

Before writing code I designed TicketLoop end to end: a Postgres schema where the database itself enforces the critical rules, state machines for every lifecycle, and an API contract.

Then I wrote each of the six hard problems, from double booking to lost events, as exact SQL and asked what happens if the process dies between any two statements. The central decision: one row, the listing, is the lock that decides who gets a ticket.

The six hard problems

The reason the project exists. Most of the API is CRUD that sets these up.

  1. 1Double booking

    100 buyers hit one listing at once; exactly one wins and 99 get a clean 409.

    Fix
    UPDATE listings … WHERE status = 'ACTIVE'. The WHERE clause is the availability check.
    Backstop
    uq_reservations_one_live_per_listing
    Built in
    M8

  2. 2Duplicate orders

    A retried POST /orders must not create a second order, even when both copies arrive at once.

    Fix
    Insert the Idempotency-Key row in the same transaction as the order and its stored response. A duplicate waits on the key, then replays the response.
    Backstop
    uq_orders_reservation
    Built in
    M9

  3. 3Duplicate or forged webhooks

    The gateway sends the same event twice, or someone fakes one.

    Fix
    HMAC over the raw body plus a 5-minute timestamp window, then a dedupe insert in the same transaction as the effect. Duplicates still get 200, so the gateway stops retrying.
    Backstop
    uq_payment_events_provider_event
    Built in
    M10

  4. 4Lost events

    The database commits but RabbitMQ is down.

    Fix
    Transactional outbox: the event row commits with the change, a relay publishes it later, and consumers ignore redeliveries.
    Backstop
    pk_processed_events (consumer, event_id)
    Built in
    M11

  5. 5Expiry racing payment

    The expiry worker must never release a ticket that was just paid for.

    Fix
    Payment and expiry both update the reservation WHERE status = 'CREATED', so only one wins. The gateway is called only after the reservation leaves CREATED. PAYMENT_PENDING is resolved by asking the gateway, never by the clock.
    Backstop
    The reservation row lock
    Built in
    M8 and M10

  6. 6Drift

    The gateway and our database disagree, usually because a webhook never arrived.

    Fix
    Reconciliation asks the gateway about unresolved payments and repairs them through the same transition functions, recording each run.
    Backstop
    Conditional updates make a re-run a no-op
    Built in
    M10

One purchase, start to finish

  1. 0
    Listing approved

    An admin approves it; buyers can now see it.

    ACTIVE
  2. 1
    Buyer reserves

    One conditional UPDATE wins the listing. The reservation holds it for 10 minutes.

    RESERVED
  3. 2
    Buyer creates the order

    Idempotency-key row, order and stored response commit together.

  4. 3
    Buyer starts payment

    Reservation and order go to PAYMENT_PENDING, then the gateway intent is created.

  5. 4
    Webhook says paid

    Verify, dedupe, payment SUCCEEDED, order PAID, outbox row: one transaction.

  6. 5
    Relay publishes

    The outbox row goes to RabbitMQ and gets published_at.

  7. 6
    Worker starts the transfer

    processed_events stops a redelivery doing it twice.

  8. 7
    Provider confirms

    Order COMPLETED, and the ticket's owner becomes the buyer, in the same transaction.

    SOLD

The right-hand strip is the listing row's status. Three things to remember:

  • The listing stays RESERVED from step 1 to step 7. That one row keeps everyone else out the whole time.
  • The ticket row changes once, at step 7. Until the provider confirms, the seller still owns it.
  • Everything that leaves the API process (steps 5 and 6, and the notifications after 7) starts from an outbox row written in the same transaction as the change.

Decisions

Who decides

Postgres is the source of truth; Redis only speeds up reads

Instead of keeping inventory in Redis

Money and inventory need transactions, constraints and durable writes. A cache can be lost or stale, which is fine for browsing and wrong for selling one ticket twice.

The listing row is the lock

Instead of plan.md's update of tickets.status

Two status columns that both mean "reserved" can disagree. One row decides who wins, and tickets.status only means valid or void.

Check and write in one UPDATE … WHERE status = :from

Instead of reading the status in Python, then writing

Two requests can both read ACTIVE and both proceed. With the check inside the UPDATE, the database decides; zero rows updated means someone got there first, which becomes a 409.

The database enforces the critical rules as well

Instead of application checks alone

The app checks first, to give a helpful error. Constraints catch bugs, and two requests that pass the same check at the same instant.

Partial unique indexes for "only one open at a time"

Instead of a plain UNIQUE

A plain unique index on listings(ticket_id) would stop a ticket being relisted after a cancel, forever. WHERE status IN (…open…) limits uniqueness to open rows.

A transactional outbox for every event

Instead of "commit, then publish to RabbitMQ"

Two systems cannot be written atomically. Commit-then-publish loses the event if the process dies in between; publish-then-commit announces a change that might roll back.

Data types

Money is BIGINT paise, in columns ending _paise

Instead of floats or rupees

Floats cannot represent 0.1 exactly; integers never round. BIGINT because INT tops out at ₹2.1 crore. The suffix stops anyone storing rupees by mistake.

Statuses are TEXT with a CHECK

Instead of a Postgres ENUM

Adding an enum value needs ALTER TYPE, which is awkward in Alembic. Changing a CHECK is one constraint swap, and states will be added.

UUID keys generated by Postgres; TIMESTAMPTZ in UTC

Instead of serial integers and zone-less timestamps

IDs appear in URLs, and sequential ones let anyone count orders or guess the next. A timestamp without a zone silently drops the offset, and expires_at < now() must be unambiguous.

API and history

404, not 403, for someone else's resource

Instead of saying "this exists but is not yours"

Nobody can probe which IDs exist. 403 is kept for "I know who you are and this action is not allowed".

No hard deletes; an append-only audit log without foreign keys

Instead of deleting rows and linking audit rows by FK

Orders, payments and audit rows must outlive what they point at. An audit insert must never fail because of an FK, and a trigger forbids UPDATE and DELETE on it.

Sync SQLAlchemy 2.0 with psycopg 3

Instead of async SQLAlchemy

One session model shared by FastAPI and the Celery workers, and fewer concepts at once. The M17 load tests can prove otherwise.

Interview questions

Answer out loud first, then open.

Why is PostgreSQL, not Redis, the source of truth for inventory?

Selling a ticket changes several rows that must all change or none: listing, reservation, audit row, outbox row. Postgres gives one ACID transaction across them, constraints that reject impossible states, and durable commits. Redis is fast but a cache can be evicted, lost on failover or stale. That is acceptable for search results, not for deciding who owns a ticket.

100 buyers press "reserve" on one ticket at the same moment. How exactly does one win?

Each runs UPDATE listings SET status = 'RESERVED' WHERE id = :id AND status = 'ACTIVE'. The first takes the row lock; the other 99 wait. Under Read Committed, when the first commits each waiter re-checks its WHERE clause against the new row, finds RESERVED, and updates zero rows, which becomes a 409. No Python reads the status first, so there is no gap between check and write. If a code path ever skipped this, the partial unique index on live reservations would reject the second one.

What state is a listing in while payment is pending, and what can move it out?

RESERVED, from the moment it is reserved until the transfer completes. Out of it:

  • transfer completes: SOLD
  • reservation expires, is cancelled or its payment fails: back to ACTIVE, or EXPIRED if the listing's own expiry passed meanwhile
  • transfer fails for good and an admin abandons it: CANCELLED, with a refund in the same transaction

The seller cannot cancel a RESERVED listing, because a buyer may be paying.

Why does a partial unique index enforce "one open listing per ticket" better than an if in Python?

Two requests can run the if at the same instant, both see no open listing, and both insert. The index is checked by the database inside the insert itself, so the second one fails with an IntegrityError no matter how the timing falls. It is partial so that cancelled or sold listings do not count and the ticket can be listed again.

What is the dual-write problem, and how does the outbox solve it?

You cannot commit to Postgres and publish to RabbitMQ atomically, so one can happen without the other. The outbox writes the event as a row in the same transaction as the change: the event exists exactly when the change does. A relay publishes unpublished rows and marks them, which can deliver the same message twice, so each consumer records (consumer, event_id) and skips anything it has seen. At-least-once delivery plus idempotent consumers gives effectively-once processing.

A client retries POST /orders because the response timed out. Why is there still one order?

The first request inserted its Idempotency-Key row, the order and the stored 201 response in one transaction. A retry with the same key conflicts on that row and gets the stored response replayed. If both arrive at once, the second insert waits for the first transaction to finish. The same key with a different body is a 422. uq_orders_reservation is the second wall.

How do you stop a forged or duplicated payment webhook from changing anything?

Forged: verify an HMAC-SHA256 of the timestamp and the raw body with compare_digest, and reject timestamps older than 5 minutes, before parsing anything. Duplicated: insert into payment_events with ON CONFLICT DO NOTHING in the same transaction as the effect. Zero rows inserted means already applied, so answer 200 and touch nothing; an error status would make the gateway retry forever.

What happens if the process dies between two SQL statements?

Inside one transaction: nothing persists. Postgres never commits a half-finished transaction; the dropped connection rolls it back. Between two transactions, such as committing PAYMENT_PENDING and then calling the gateway, the saved state says exactly where it stopped, and reconciliation finishes the job using the same idempotency key. That is why each hard problem was written as SQL with a "dies after" table.

Gaps fixed in plan.md

  • Two status columns for one fact. Reservation moved to the listing row; tickets.status now only means valid or void. For the same reason listings.verification_status was dropped: PENDING_VERIFICATION and REJECTED already say it.
  • An index on a column that did not exist. plan.md indexes listings(event_id, status) but listings had no event_id. Copied it over, which is safe because a ticket never changes event.
  • Columns the requirements list but the schema lacked: orders.listing_id, payments.idempotency_key and provider_response, listings.original_price_paise (the price cap needs both prices in one row).
  • Eleven missing tables, including refresh_tokens, idempotency_keys, refunds, reconciliation_runs, processed_events and disputes.
  • A reserved name. SQLAlchemy's declarative base owns the attribute metadata, so audit_logs.metadata became details.
  • A clock that does not move. now() is the transaction's start time, so transactions must stay short or expiry checks compare against a stale clock.
