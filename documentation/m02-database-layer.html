The 30-second answer

I put the business rules in the database, not only in Python. A partial unique index allows one open listing per ticket. CHECK constraints cap the resale price at what the seller paid. A trigger makes the audit log append-only. Each test checks which rule fired, by name.

Each request runs in one transaction. get_db commits when the route succeeds and rolls back on any error, and it finishes before FastAPI sends the response. A commit that fails reaches the client as an error, never as a 200 for data that was never saved.

The rules Postgres enforces

The app checks these first so it can return a helpful error. The database is the backstop for a bug, or for two requests that pass the same check at the same instant.

  • One open listing per ticketA unique index on ticket_id, but only over rows WHERE status IN ('DRAFT', 'PENDING_VERIFICATION', 'ACTIVE', 'RESERVED'). Once a listing is sold or cancelled, the ticket can be listed again.uq_listings_one_open_per_ticket
  • No markupThe asking price is at most the original price and at least ₹1. The original price is copied onto the listing because a CHECK can only see its own row.ck_listings_price_cap ck_listings_min_price
  • A rejection has a reasonstatus <> 'REJECTED' OR rejection_reason IS NOT NULLck_listings_rejection_reason
  • Known statuses onlyEvery status column is TEXT with a CHECK that lists the allowed values.ck_*_status
  • One account per emailEmails are unique and must be stored in lower case, so "A@x.in" and "a@x.in" cannot become two accounts.uq_users_email ck_users_email_lowercase
  • A real ticket is registered onceThe provider's reference is unique within an event.uq_tickets_event_provider_reference
  • History cannot be rewrittenA BEFORE UPDATE OR DELETE trigger raises "audit_logs is append-only". The table has no foreign keys, so writing an audit row never fails because a reference is missing.forbid_update_delete()

One request, one transaction

  1. 1
    FastAPI resolves DbSession

    get_db takes a Session from app.state.session_factory. No connection is opened yet.

  2. 2
    The route runs

    The first statement checks out a pooled connection and opens a transaction. Changes wait in the session; with autoflush=False, SQL goes out only on a flush, a commit or a query I run.

  3. 3
    The route returns, get_db commits

    The flush sends the INSERTs and UPDATEs, then COMMIT. A constraint can still fail at this point, which is why the commit has to finish before the response goes out.

  4. 4
    Any error rolls everything back

    The exception goes through the M1 handlers and becomes problem+json. Nothing from the request is saved.

  5. 5
    The session closes, then the response is sent

    The connection goes back to the pool. Loaded objects stay readable, so FastAPI can serialise them after the session has closed.

What a commit sends

BEGIN                                    # implicit, before the first statement
INSERT INTO listings (ticket_id, event_id, seller_id, asking_price_paise, …)
  VALUES (…) RETURNING id, status, created_at, updated_at
COMMIT                                   # or ROLLBACK, and nothing is kept

RETURNING comes from eager_defaults=True: the values Postgres generates come back in the same round trip.

The experiment: two buyers, one seat

Both sessions send UPDATE seats SET status = 'RESERVED' WHERE id = 1 AND status = 'ACTIVE'. A leaves its transaction open.

 0.16s  A: claims the seat -> 1 row updated, transaction left open
 0.16s  B: sends the same claim
 1.17s  watcher: B is active, waiting on Lock/transactionid, blocked by [226]
 1.17s           (A is pid 226)
 3.19s  A: COMMIT
 3.19s  B: wakes up, re-checks WHERE, updates 0 rows
 3.19s     after waiting 3.02s
 3.19s  final status: RESERVED, claimed exactly once
  • B waits on A's transaction, not on a query. A row lock is held until COMMIT or ROLLBACK. pg_blocking_pids() names who holds it.
  • Once A commits, B reads the new row version and checks the WHERE clause again. The row is now RESERVED, so B updates 0 rows. It gets no error and no lost update.
  • This is the M8 reservation. The WHERE clause is the availability check, and the row count says who won. A long transaction makes every other buyer wait, so the reservation transaction must stay short.

Decisions

Schema

A partial unique index for "one open listing"

Instead of an if check in Python, or a plain UNIQUE (ticket_id)

Two requests can both run the if, both see no listing, and both insert. The index is checked inside the INSERT itself, so the second insert waits for the first transaction and then fails. A plain UNIQUE would block relisting forever after a cancellation.

Status as TEXT with a CHECK

Instead of a Postgres ENUM type

Changing the allowed values is one migration that drops and re-adds the CHECK. An ENUM value can be added or renamed, but removing one means building a new type and converting the column.

Money as BIGINT paise

Instead of float or NUMERIC rupees

Integer arithmetic is exact. ₹2,500 is stored as 250000, with no rounding and no decimal handling in Python.

UUID ids from gen_random_uuid()

Instead of serial integers, or uuid4() in Python

Nobody can guess the next id or count our listings from the URLs. Because the database fills it in, a psql insert, a migration and a worker all get ids the same way.

Named constraints through a naming convention

Instead of names Postgres makes up

The error says ck_listings_price_cap, so the tests and later the API error mapping can tell which rule fired. Alembic can drop a constraint by a name it knows in advance.

Only the tables M2 needs, no query indexes yet

Instead of creating the whole M0 schema now

Each later module adds its own tables and indexes in its own migration, next to the queries that need them. That is how a real schema grows, and every index has a query that justifies it.

Sessions

The request is the transaction

Instead of services calling commit()

A request saves all of its changes or none of them. Service code can call other services without worrying about half-finished writes.

Depends(get_db, scope="function")

Instead of FastAPI's default request scope

With the default scope, the code after yield runs after the response has been sent, so a failed commit would reach the client as a 200. A test proves it: remove the scope and that test fails.

expire_on_commit=False and eager_defaults=True

Instead of SQLAlchemy's defaults

The response is built after the session has closed. An expired attribute would try to reload from that closed session and raise DetachedInstanceError. RETURNING loads updated_at during the UPDATE itself.

updated_at through the model's onupdate

Instead of a trigger on every table

One rule in one place, covering every ORM and Core update. Raw SQL typed in psql is not covered, and that is acceptable for a timestamp.

Migrations and tests

Migrations as a separate job

Instead of running upgrade head when the app starts

Several API containers start together for the M8 race test and the load tests. They would all try to migrate at the same moment. A single job migrates once, and every API container waits for it.

The test schema is built by the migrations

Instead of metadata.create_all()

Tests run against exactly what production gets, trigger included. A separate test then checks that the models and migrations agree: the same comparison alembic check makes must find no differences.

Each test runs inside one transaction that is rolled back

Instead of truncating tables between tests

The session joins the test's transaction with create_savepoint, so a commit() in app code only releases a savepoint. Every test starts from an empty database, and a test takes milliseconds.

Interview questions

Answer out loud first, then open.

What does session.commit() send to Postgres?

First a flush: the INSERT, UPDATE and DELETE statements for every pending change, ordered so that foreign keys are satisfied, with RETURNING for the values the server generates. Then COMMIT. The BEGIN went out without being asked, before the first statement of the transaction. After the commit the session releases its connection, and the next statement starts a new transaction.

Why does a partial unique index enforce "one open listing" better than an if check in Python?

The if is a read followed by a write, with a gap in between. Two requests can both read "no open listing" and both insert. The index check is part of the INSERT itself. If another transaction has just inserted the same key, the second insert waits for it to finish and then fails with a unique violation. The index also protects against writers that never run my Python: an admin script, a worker, a bug. Making it partial means closed listings don't count, so a ticket can be listed again.

Two transactions UPDATE the same row. What happens?

The first one takes a row lock that it holds until it commits or rolls back. The second one blocks. In pg_stat_activity it shows wait_event_type = Lock, wait_event = transactionid. When the first one commits, the second one reads the new row version and checks its WHERE clause again (this is Read Committed). If the row no longer matches, it updates 0 rows. If the first one rolls back instead, the second one updates the original row.

What can Alembic autogenerate not detect?

Anything that is not in the SQLAlchemy metadata: triggers, functions and views. Renames, which show up as a drop plus an add, so the data would be lost. A CHECK added to, removed from or changed on an existing table. It does write CHECKs and partial indexes when it creates a new table. That is why every generated migration has to be read before it runs, and why my trigger is hand-written in both upgrade() and downgrade().

How do your tests get a clean database each time without being slow?

Once per run, the ticketloop_test database is dropped, created again and migrated to head. Each test then opens one connection, begins a transaction, and gives the session that connection with join_transaction_mode="create_savepoint". A commit in app code releases a savepoint. At teardown the outer transaction rolls back, and everything the test wrote disappears.

Why does get_db need scope="function"?

With the default scope, the code after yield in a dependency runs after the response has been sent. My commit is in that code. A commit that failed, say on a unique violation, would be logged, but the client would already have a 200. With scope="function" the dependency finishes before the response is built, so the failure becomes a 500, and later a 409. I proved it by removing the scope: the failed-commit test fails.

Why turn off expire_on_commit? What is the risk?

After a commit, SQLAlchemy normally expires every loaded object, so the next attribute read reloads it from the database. My response is serialised after the session has closed, so that reload would fail. The risk is reading stale values if another transaction changes the row afterwards. That doesn't matter here, because the request ends right after the commit.

Why TEXT and CHECK for statuses instead of an ENUM?

Status sets change as the product grows. Changing a CHECK means dropping it and adding the new one in a single migration. An ENUM type lets you add or rename a value, but removing one means building a new type and converting every column that uses it. TEXT costs a few more bytes per row, which doesn't matter at this scale, and the CHECK still rejects any unknown value.

Why store money as BIGINT paise?

Floats cannot represent most decimal amounts exactly (0.1 + 0.2 is not 0.3), and those errors pile up in totals and refunds. NUMERIC is exact, but every value then needs decimal handling in Python. Integer paise are exact, fast and simple. BIGINT rather than INTEGER, which tops out near ₹2.1 crore in paise.

Traps and fixes

  • FastAPI's default dependency scope commits too late. The code after yield runs after the response has been sent. Fixed with scope="function", and a test fails if the fix is removed.
  • Reading updated_at after the session closed raised DetachedInstanceError. The UPDATE expired it. Fixed with eager_defaults=True, which loads it with RETURNING.
  • now() is the time the transaction started. Two updates inside one rolled-back test transaction get the same timestamp, so the updated_at test uses real commits in separate transactions and cleans up afterwards.
  • Autogenerate cannot see triggers. I wrote the trigger and its DROP by hand. The round-trip test checks that the function is gone after downgrade base.
  • The plan said autogenerate misses CHECKs and partial indexes. For a new table it writes both. What it misses is a later change to them. I corrected the plan.
  • uv run python scripts/x.py cannot import app. Python puts the script's own folder on the import path, not the repo root. Run it as a module: python -m scripts.lock_experiment.
  • Postgres DDL is transactional. The whole migration runs in one BEGIN … COMMIT, so a migration that fails halfway leaves nothing behind. MySQL and Oracle commit each DDL statement on its own.
